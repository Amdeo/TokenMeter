# Contributing

## Before you start

- Use macOS 14 or later and **Xcode 26 or later**. The project uses macOS 26 SDK symbols.
- Fork and clone the repository, then create a focused branch from current `main`.
- The application UI is Simplified Chinese. Keep user-facing wording consistent with the existing UI unless the change is specifically about localization.
- Never commit API keys, OAuth tokens, cookies, credential files, browser exports, or screenshots that expose them.

## Build and test offline

The project has no third-party dependencies. Build and run the existing Swift Testing suite without network access after Xcode has the required SDK installed:

```bash
xcodebuild -project TokenMeter.xcodeproj -scheme TokenMeter \
  -configuration Debug test CODE_SIGNING_ALLOWED=NO
```

For a source build without tests:

```bash
xcodebuild -project TokenMeter.xcodeproj -scheme TokenMeter \
  -configuration Debug build CODE_SIGNING_ALLOWED=NO
```

Use the `TokenMeter` scheme. Keep changes focused and verify the behavior you changed; include the command or manual scenario in the pull request.

## Provider changes

Read and follow the [provider development guide](docs/provider-development.md) before adding or changing a provider. In particular, use stable provider IDs, keep credentials out of subscription metadata and logs, add parsing and failure coverage where appropriate, register new source and icon assets with the Xcode target, and update the README provider table when support changes.

Provider APIs can be private, unstable, or authorization-sensitive. Do not guess undocumented endpoint behavior and do not submit captured account data as test fixtures.

## Issues and pull requests

GitHub Issues are public. Search existing issues first, then use the bug or provider-request template. Provide reproducible, non-sensitive information only; redact URLs and identifiers if they contain credentials.

For a pull request:

1. Describe the user-visible behavior and the affected provider or screen.
2. Explain how you verified the change, including any relevant command or manual scenario.
3. Include screenshots for visible UI changes after removing sensitive information.
4. Keep unrelated changes out of the pull request.

Submitting a contribution does not grant a promise of review, merge, support, or release timing.

## Packaging a release

Releases are tag-driven. Bump `MARKETING_VERSION` (and `CURRENT_PROJECT_VERSION`)
in `TokenMeter.xcodeproj`, update `CHANGELOG.md`, land everything on `main`, then
push an annotated tag:

```bash
git tag -a v0.2.0 -m "TokenMeter 0.2.0" && git push origin v0.2.0
```

The `Release` workflow runs the test suite, builds the universal (arm64 + x86_64)
unsigned archive, writes `TokenMeter-<version>-macos-universal.zip` plus its
SHA-256 checksum, and attaches both to the GitHub Release for that tag. Tag a
commit whose CI is green; use `workflow_dispatch` to rebuild or repair a tag that
already exists. The workflow owns the release assets — do not upload a second
archive by hand.

To reproduce the same archive locally (offline checks, or signed distribution),
run `bash scripts/package-release.sh` from a checkout with Xcode 26+. It builds
both Apple Silicon and Intel slices and writes a ZIP and SHA-256 checksum to
`dist/`. Existing unrelated files in the output directory are preserved.
The default archive is unsigned; do not describe it as notarized.

For signed distribution, install a Developer ID Application identity and create
a `notarytool` keychain profile using Apple's documented credential workflow.
Set `DEVELOPER_ID_APPLICATION` and `NOTARYTOOL_PROFILE` before running the script.
The signed path submits the app to Apple for notarization, staples the ticket,
and packages the stapled app. Never put signing credentials in a pull request.
Signing and notarization require maintainer credentials and are separate from CI.

Verify the checksum from `dist/` with `shasum -a 256 -c <archive>.zip.sha256`.
Install on a clean machine and verify the app version, launch, sign-in and quota
display before uploading artifacts to a GitHub Release. Keep release notes tied
to the exact tag rather than describing unreleased `main` features.

The archive name comes from `CFBundleShortVersionString`, which the target build
settings define as `$(MARKETING_VERSION)`. Bump it before tagging: the local
script refuses to overwrite an existing archive for that version, and the release
workflow fails when the built version does not match the tag.

The app icon is original artwork generated by `swift scripts/generate-app-icon.swift`.
Third-party provider logos remain their owners' assets; do not add new logos
without documenting their source and permission to redistribute.
